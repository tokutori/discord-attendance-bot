Discord 活動時間記録 Bot 仕様書

版: v1.0
対象: 鳥人間チームのメンバーごとの活動時間記録
実装言語: Rust
保存先: SQLite
作成日: 2026-08-06
最終更新日: 2026-08-09

1. 目的

Discord 上で各メンバーが活動開始・活動終了を記録し、個人ごとの活動履歴および月間活動時間を確認できる Bot を実装する。

本システムは、日本語圏のクラブ・チームが1つのGuildごとにセルフホストする用途を対象とする。給与計算や法令対応を目的とする厳密な勤怠管理システム、中央サービス型のマルチGuild SaaS、多言語製品ではない。活動量を概算記録し、本人が後から修正または完全消去できることを重視する。

2. 基本構成

  • Discord の Slash Command を操作入口とする。
  • Rust 製 Bot が command を処理する。
  • 活動記録は SQLite に保存する。
  • Google Spreadsheet 等への同期は行わない。
  • 各メンバーは自分の記録だけを閲覧・修正・削除できる。
  • 1つの実行プロセスは1つのDiscord GuildとローカルSQLite DBを担当する。
Discord
  └─ /attendance ...
       └─ Rust Bot
            └─ SQLite

2.1 運用モード

引数なしのstandalone運用を既定とし、DISCORD_GUILD_IDとDATABASE_URLで1つのGuildと永続SQLite DBを指定する。既存運用との互換性のため、起動引数testまたはreleaseによる分離設定も使用できる。

モードGuild IDデータベース起動例
standaloneDISCORD_GUILD_IDDATABASE_URLcargo run --release
testDISCORD_TEST_GUILD_IDDATABASE_URL_TESTcargo run -- test
releaseDISCORD_RELEASE_GUILD_IDDATABASE_URL_RELEASEcargo run --release -- release

各モードとも指定したGuildにのみcommandを登録し、global commandは使用しない。永続運用ではインメモリDBを拒否し、同じGuild・DB・tokenに対する複数プロセス起動をサポートしない。

ATTENDANCE_STATUS_MODEはdisabled、count、namesから選択する。countは人数だけ、namesは人数とDiscord表示名をTopicとActivityへ表示し、disabledでは更新しない。Channel IDがある場合の既定値は個人情報を表示しないcount、Channel IDがない場合はdisabledとする。有効時だけ専用Channel IDを必須とする。更新間隔はATTENDANCE_STATUS_REFRESH_SECONDSで設定する。Activityの種別はWatchingとし、128文字、Topicは1024文字まで保持する。

4. 状態モデル

利用者ごとの状態は、活動中と非活動中の2状態とする。

現在状態 操作 遷移後 処理
非活動中 start 活動中 新しい未終了記録を作成する。
活動中 end 非活動中 現在の未終了記録へ終了時刻を設定する。
非活動中 continue 活動中 直近の終了済み記録の終了時刻を削除する。
活動中 start 活動中 重複開始として no-op にする。
非活動中 end 非活動中 重複終了として no-op にする。
活動中 continue 活動中 すでに活動中であることを表示する。

自動終了後の入力

BotはATTENDANCE_TIMEZONEの翌日0:00に、開始・再開後に次に到来するATTENDANCE_AUTO_END_TIMEを終了時刻として自動終了する。既定値はAsia/Tokyoと21:00で、disabledにより自動終了を無効化できる。Bot停止中の未処理分は次回起動時に補完する。

自動終了後にユーザーが end、または確認済みの edit・delete を実行した場合は、対応する自動終了イベントを訂正済みにしてユーザー入力を正とする。同じ記録を continue した後に再び終了を忘れた場合は、別の自動終了イベントとして処理する。次のユーザー操作時には、自動終了した記録と修正方法を通知し、応答送信の成功後にだけ通知済みにする。

5.4 /attendance continue

直前の /attendance end を取り消す。新しい記録は作らず、直近の終了済み記録の ended_at を NULL に戻す。

想定例

13:00 start
18:00 end
18:05 continue
21:00 end

最終的な記録は 13:00 ～ 21:00 の1件となる。

正常時

活動を継続状態に戻した。

開始時刻: 2026年8月6日 13:00
取り消した終了時刻: 2026年8月6日 18:00
現在の経過時間: 6時間05分
記録ID: #128

すでに活動中の場合

すでに活動中である。

開始時刻: 2026年8月6日 13:00
経過時間: 6時間05分
記録ID: #128

過去記録がない場合

継続できる直近の活動記録がない。

5.5 /attendance revert

start、end、continue、edit、delete の直前の成功した変更操作を1件取り消す。start は作成記録を soft delete、end は終了前、continue は continue 前、edit は編集前、delete は削除前の状態へ復元する。最初の呼び出しでは変更前後と5文字の確認IDを表示するだけで、/attendance confirm までDBを変更しない。

revert 自体は操作履歴に追加しないため、1回確定した後に再び revert と confirm を行うと、さらに前の成功した変更を順に取り消す。たとえば start → end → revert → confirm → revert → confirm では、1回目に end を取り消して活動中へ戻し、2回目に start を取り消して作成記録を soft delete する。対象がない場合は安全なno-opとし、現在状態がプレビュー時と異なる場合や復元によって活動区間が重複する場合は確定せず、確認IDを使用済みにする。

5.6.1 /attendance list

guild内で現在活動中の全メンバーを ephemeral Embed の名簿として表示する。役割、代（整数の昇順）、name_reading（五十音順）の階層で並べ、本名と活動開始時に保存したDiscord表示名を併記する。Embed descriptionでは # 役割、## 代、- 本名（Discord表示名） のMarkdownを使用する。ユーザー入力は改行を空白へ変換してMarkdown記号をescapeする。Discordの文字数上限を超える名簿は階層見出しを繰り返して複数のephemeral Embedへ分割し、メンバーを欠落させない。役割・代の未設定グループと、userconfigがすべて未設定のメンバーは設定済みメンバーより後に表示する。読みが未設定の場合も名簿から除外せず、本名またはDiscord表示名を安定したフォールバック順に使用する。

5.9 /attendance edit

本人の既存記録を修正する。

最初の実行では変更前後を表示し、5分間有効な5文字の確認IDを発行する。この時点では DB を変更しない。/attendance confirm に確認IDを指定したとき、プレビュー時の状態と現在の状態が一致すれば修正を確定する。一致しなければ安全のため確定しない。

引数

引数必須例意味
record必須128修正対象の記録ID。
start任意2026-08-06 13:30修正後の開始日時。
end任意2026-08-06 18:00修正後の終了日時。
note任意電装作業修正後の備考。

start、end、note のうち少なくとも1つを指定する。本人の記録だけを修正可能とする。

5.10 /attendance delete

本人の活動記録を削除する。

最初の実行では削除対象の内容を表示し、5分間有効な確認IDを発行する。/attendance confirm で確定するまで DB は変更しない。確定後は deleted_at を設定する。

引数

引数必須例意味
record必須128削除対象の記録ID。

確認IDによる /attendance confirm で削除を明示的に確認する。DB 上では物理削除せず、deleted_at を設定する soft delete とする。

5.11 /attendance confirm

edit、delete、revert が発行した5文字の確認IDを指定して変更を確定する。確認IDの有効期限は発行から5分で、使用済みIDは再利用できない。確認前に別の変更が行われ、プレビュー時の状態と一致しなくなった場合、または revert 対象が同一ユーザーの最新未取り消し操作ではなくなった場合は確定せず、要求を無効化する。

引数

引数必須例意味
id必須AB3KQプレビュー時に発行された確認ID。

5.12 /attendanceexport help / export / userconfig / clearuserconfig

/attendanceexport help は月次ファイル出力の使い方を Embed で表示する。

/attendanceexport export は month を必須とし、YYYY-MM 形式の指定月についてDiscord表示名あり版と本名のみ版の CSV と PDF、合計4ファイルを同時に生成する。mode は preview または publish で、既定値は preview とする。全メンバーの本名を含み得るため、実行者には「サーバー管理」権限を要求する。Botにはメッセージ送信・Embed・ファイル添付権限を要求する。preview は実行者だけに表示する。publish はconfirm_public:trueを必須とし、生成成功時のみ別の公開メッセージとして送信し、実行Guild・user・対象月を監査ログへ記録する。処理開始、エラー、公開成功の確認はどちらのmodeでもephemeralとする。

/attendanceexport userconfig は本人の generation（代・整数）、real_name（本名）、role（代表、新入生、班名などの自由記述）、name_reading（活動中名簿の五十音順に使う読み）を設定する。読みはひらがな・カタカナを受け付け、ひらがなへ正規化して保存する。引数なしでは現在値を ephemeral Embed で表示し、一部の引数だけを指定した場合は指定していない設定を保持する。clearuserconfigは全プロフィール項目を解除する。

表の構造

表の縦方向は対象月に記録があるユーザー、横方向は対象月の日数にユーザー情報列と合計列を加えたものとする。4ファイルは /attendance list と共通の比較処理により、役割、代（昇順）、名前の読み（五十音順）で並べる。Discord表示名ありCSVでは代・本名・役割・Discord表示名を個別の列とし、PDFではユーザー情報欄にまとめる。本名のみ版はDiscord表示名を含めず、本名未設定時は「未設定」と表示する。CSVのユーザー入力列は表計算ソフトの数式として評価される危険な先頭文字を無害化し、その後でCSV構文をescapeする。活動時間があるセルは 時間:分 形式で表示する。PDFの活動時間0セルは空欄、CSVの活動時間0セルは 0:00 とする。PDFの文字はセル内で上下中央揃えとし、長い代・本名・役割・Discord表示名は省略せず折り返しと文字サイズ調整を行う。活動中の記録は出力時点までを暫定値として含める。

注記

指定月がまだ終了していない場合は、暫定集計であることを応答と PDF に記載する。指定月の翌月1日に出力した場合は、ユーザーが修正する可能性があるため確定版ではないことを応答と PDF に記載する。

6. 時刻の扱い

  • DB には UTC の Unix timestamp を保存する。
  • 利用者向け表示はATTENDANCE_TIMEZONEで指定したIANA timezone（既定Asia/Tokyo）で行う。
  • at には HH:MM 形式を許可する。start は当日の時刻として解釈して未来なら拒否し、end は現在から見て最も近い過去の同時刻として解釈する。
  • edit には YYYY-MM-DD HH:MM 形式を使用する。
  • 終了時刻が開始時刻より前になる場合、および edit で未来時刻を指定した場合は保存せずエラー表示する。

7. SQLite schema

v1.0では本番運用前の設計見直しとしてmigration履歴をリセットし、migrations/0001_initial_schema.sql から新規DBを作成する。v0.0のテストDBとはmigration互換性を持たせないため、Bot停止後に旧テストDBと対応する -wal・-shm を削除して再作成する。本番運用開始後のmigrationにはこの方法を使用しない。

CREATE TABLE attendance_sessions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    guild_id INTEGER NOT NULL,
    user_id INTEGER NOT NULL,
    display_name TEXT NOT NULL,

    started_at INTEGER NOT NULL,
    ended_at INTEGER,
    open_since INTEGER,

    note TEXT,

    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    deleted_at INTEGER,

    CHECK (
        ended_at IS NULL
        OR ended_at >= started_at
    ),
    CHECK (
        (ended_at IS NULL AND open_since IS NOT NULL AND open_since >= started_at)
        OR (ended_at IS NOT NULL AND open_since IS NULL)
    ),
    UNIQUE (id, guild_id, user_id)
);

CREATE UNIQUE INDEX attendance_sessions_one_open_per_user
ON attendance_sessions (guild_id, user_id)
WHERE ended_at IS NULL
  AND deleted_at IS NULL;

CREATE INDEX attendance_sessions_user_history
ON attendance_sessions (
    guild_id,
    user_id,
    started_at DESC
)
WHERE deleted_at IS NULL;

open_since は現在の連続活動開始点を表し、自動終了後の continue ではcontinue時刻へ更新する。INSERT/UPDATE triggerにより、同一guild・userの削除されていない活動区間どうしの重複を拒否する。

attendance_changes は、各成功した変更操作についてguild・user・対象記録・操作種別・操作前後の開始時刻・終了時刻・連続活動開始点・備考・削除時刻を保存し、reverted_at で取り消し済みかを管理する。取り消し処理は最新の未取り消し変更を対象とし、現在状態が保存済みの変更後状態と一致しない場合は安全のため実行しない。session・guild・userを組にした外部キーで所有者の不一致を拒否する。

pending_attendance_actions は edit、delete、revert の確認要求とプレビュー時の open_since を保存する。確認IDは5文字で発行から5分間有効、要求者のguild・userに限定し、確定後、期限切れ、状態不一致、重複区間発生時は再利用できない。change_id によってrevert対象の変更へ関連付ける。

attendance_auto_end_events は独立したイベントID、自動終了時刻、適用時刻、適用時点の最新変更ID、通知済み時刻、ユーザー入力による訂正時刻を保存する。同じsessionでも continue 後の再自動終了を別イベントとして保持し、未訂正のイベントはsessionごとに最大1件とする。自動終了の適用後に別の変更履歴が追加されたイベントは、後日の end による自動訂正の対象にしない。

attendance_user_profiles はguild・userごとに代、本名、役割、名簿用の名前の読みを保存する。Discord user IDを本人識別の主キーとし、表示名や本名は識別子として使用しない。本名とDiscord表示名には文字種・構造・一意性を仮定せず、入力された文字列を表示用に保持する。

8. データ操作規則

  • 未終了記録は、同一 guild・同一 user につき最大1件とする。
  • 重複 start と重複 end はエラー終了させず、no-op として現在状態を表示する。
  • continue は新しい記録を作らず、直近終了記録を再び未終了状態へ戻す。
  • 自動終了は設定timezoneの毎日0時に実行し、開始・再開後に次に到来する設定時刻を終了時刻として扱う。無効化可能で、Bot停止中の未処理分は次回起動時に補完する。
  • 自動終了後のユーザー end は自動終了を取り消し、ユーザー入力を正として保存する。
  • 編集・削除時は、SQL 条件に guild_id と user_id を含める。
  • 削除済み記録は通常の検索・集計から除外する。
  • /attendance erase confirmation:DELETEは本人所有の全データを外部キーcascadeを含めて物理削除する。バックアップと公開済み帳票は別途保持方針に従う。
  • 表示名は参考情報として保存する。本人識別には Discord user ID を使用する。
  • 成功した start、end、continue、edit、delete は revert 用の操作履歴を作成する。no-op や失敗した操作は履歴に追加しない。
  • 同一ユーザーの削除されていない活動区間は重複させない。競合し得る確認・変更処理は即時write transactionで直列化し、WALのbusy/lockedにはbusy timeoutと限定的な再試行を使用する。

9. 月間集計

対象月に重なる終了済み記録を取得し、月範囲との重複時間だけを加算する。活動中の記録は /attendance month の確定済み集計には含めない。

SELECT
    id,
    user_id,
    display_name,
    started_at,
    ended_at,
    note
FROM attendance_sessions
WHERE guild_id = ?
  AND user_id = ?
  AND deleted_at IS NULL
  AND ended_at IS NOT NULL
  AND started_at < ?
  AND ended_at > ?
ORDER BY started_at ASC;

各記録の月内時間は次の式で求める。

effective_start = max(started_at, month_start)
effective_end   = min(ended_at, month_end)
duration        = max(effective_end - effective_start, 0)

1回あたり平均は total / session_count、1日あたり平均は total / elapsed_calendar_days、1週間あたり平均は total * 7 / elapsed_calendar_days とする。秒未満は整数除算で切り捨てる。elapsed_calendar_days は当月では今日を含む経過暦日、過去月では全日数、未来月では0とする。

9.1 月次ファイル出力

/attendanceexport export は同じ月内重複計算をユーザー別・日別に展開し、attendance_user_profiles の代・本名・役割・名前の読みを反映したDiscord表示名あり版・本名のみ版のCSVとPDF（計4ファイル）にする。全ファイルは活動中名簿と共通の比較処理で並べる。ファイル出力では活動中の記録も出力時点までの暫定値として含める。出力表はユーザー行、日付列、合計列で構成する。生成後はinteraction固有の添付サイズ上限を各ファイルについて検査し、超過時は送信しない。

PDF 生成には printpdf を採用する。表の配置・改ページ・文字レイアウトは Bot 側で明示的に制御し、保存時に PdfSaveOptions.subset_fonts = true を指定する。これにより、PDF に現れる文字のグリフだけをフォントから埋め込み、CJK フォント全体の埋め込みによる添付サイズ増大を避ける。日本語フォントは環境依存のため、ATTENDANCE_PDF_FONT_PATH でTTF・OTF・TTCを指定できる。

genpdf は TableLayout など高レベル API が便利だが、今回の使用文字だけのサブセット埋め込みを明示的に保証しにくいため採用しない。lopdf / lopdf-table は PDF 構造や表の細かな後処理が必要になった場合の候補とする。

10. 応答の表示方針

  • 通常の操作結果は原則として ephemeral response とする。
  • Slash Command の利用者向け応答は、成功結果・想定内の入力エラー・権限エラーを含め、原則として本人だけが見られる ephemeral Embed を使用する。
  • history、month、help は専用レイアウトの Embed を使用する。
  • /attendanceexport userconfig は現在値または更新後の代・本名・役割・名前の読みを ephemeral Embed で表示する。
  • /attendanceexport export は preview では4ファイルを ephemeral に添付する。publish でも処理中・エラー・成功確認はephemeralとし、生成成功後だけ別の公開メッセージへ4ファイルを添付する。
  • 自動終了通知はユーザー応答への付加に成功した後で通知済みにする。公開export本文やPDFには実行者個人の通知を含めない。
  • コマンドエラーは入力形式、PDFフォント、添付サイズ、データベース、Discord通信などの種別に分類し、原因と対処を Embed で説明する。秘密情報や認証情報は表示しない。
  • revert は直前の成功した変更操作を1件取り消し、操作内容と対象記録を Embed で説明する。revert 自体は履歴に積まれないため、連続実行では過去の変更を順に取り消せる。
  • 表示内容は簡潔にし、記録ID、時刻、時間、備考を中心とする。
  • 備考がない場合は空の備考欄を表示しない。
  • Embed の Discord 上限（説明 4096 文字、フィールド値 1024 文字、メッセージ全体 6000 文字）を超えないようにする。履歴が長い場合は表示本文を安全に省略する。
  • Bot の Activity とチャンネル Topic は Embed ではなく、それぞれの Discord 表示領域で更新する。
